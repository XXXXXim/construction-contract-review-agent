# P0. 문제 정의

> **사후 작성 (2026-11-08).** 이 프로젝트는 설계(SPEC)부터 시작했다. 개발 프로세스를 P0~P7로 정한 뒤
> 빠진 단계를 거꾸로 채운 문서다. 그때 정한 것과 지금 다시 정리한 것을 구분해서 적는다.

## 한 줄 요약
**원청의 계약 검토 담당자**가 하도급 계약서를 받았을 때, 표준계약서·하도급법보다 **수급사업자에게 불리하거나 표준에서 벗어난 조항**을 **원문 근거와 함께** 자동으로 찾아준다.

## 왜 하는가
| 항목 | 내용 |
|---|---|
| 개인 목표 | SK에코플랜트 AI Application Engineer 신입 지원(서류 마감 11/15)용 포트폴리오. 기능 수보다 **측정된 성능 숫자**로 증명한다 |
| 과제 출처 | 보스가 전달한 배경: SK에코플랜트가 '1인 1 AI 에이전트' 체계를 발표했고, 사내 과제 중 하나가 "대외 공문 및 계약 검토"다. **이 프로젝트는 그 과제를 공개 자료만으로 재현한다.** 사내 자료는 쓰지 않고 가정하지도 않는다. 이 배경은 보스가 전달한 정보이며 이 문서에서 따로 검증하지 않았다 |
| 창업 관점 | 2차 고객(중소 하도급 업체)용 "불리한 조항 알림" 서비스로 확장할 수 있는지 본다 |

## 고객과 문제
| 항목 | 1차 고객: 원청 계약 검토 담당자 | 2차 고객: 중소 하도급 업체 |
|---|---|---|
| 하는 일 | 하도급 계약서를 표준계약서·하도급법과 대조해 문제 조항을 찾는다 | 원청이 내민 계약서에 서명할지 판단한다 |
| 페인포인트 (가정) | 계약서 하나에 조항이 50~60개, 대조할 기준 문서가 3종이라 사람이 일일이 대조해야 한다 | 법무 인력이 없어 불리한 조항을 모르고 서명한다 |
| 지금 해결 방법 (가정) | 사람이 직접 대조하고, 체크리스트를 쓰고, 법무팀에 문의한다 | 감으로 판단하거나 외부 자문을 받는다 (비용 부담) |
| 일반 LLM 으로 해결 안 되나 | 계약서를 통째로 넣으면 **근거 없는 그럴듯한 지적(환각)**이 섞이고, 어느 조문 기준인지 확인하기 어렵다 | 같음 |

> ⚠️ 위 페인포인트는 **고객 인터뷰로 검증하지 않은 가정**이다. 아래 "가정과 검증 방법" 참고.

## 핵심 아이디어
1. **조항 단위로 쪼개서** 대응하는 표준 조항과 1:1로 비교한다
2. 숫자로 판정할 수 있는 항목(기한 일수, 비율)은 **LLM 없이 규칙으로** 판정한다. 기준값은 원문 인용과 함께 둔다
3. LLM 이 낸 근거 인용이 **기준 문서에 실제로 있는 문장인지 코드로 검증**하고, 없으면 그 지적을 버린다

## 성공 지표
| 지표 | 목표 | 측정 방법 | 현재 (2026-11-08) |
|---|---|---|---|
| Recall (주입한 변형을 잡은 비율) | baseline 보다 높게 | `make eval`, 합성 라벨 24개 | 실제 LLM 측정 전. FakeLLM 기준 v2 0.92 |
| Precision (지적 중 맞은 비율) | baseline 보다 높게 | 같음 | 실제 LLM 측정 전. FakeLLM 기준 1.00 |
| Citation accuracy (근거 조항이 맞은 비율) | 측정해서 기록 | 같음 | FakeLLM 기준 1.00 |
| baseline → v2 개선 폭 | **숫자로 설명 가능한 개선 1개 이상** | `--compare` 비교표 | **미측정 (API 키 없음)** |
| 계약서당 처리 시간·비용 | 기록 | 같음 | FakeLLM 0.5초. 실제 LLM 미측정 |

> 목표치를 "recall 0.9" 같은 고정 숫자로 정하지 않은 이유: 합성셋 난이도가 실제와 다르기 때문이다. 대신 **같은 평가셋에서 baseline 대비 개선**을 성공 기준으로 둔다.

## 비범위 (Non-goals)
- 로그인, 회원 관리, DB 서버, 배포 인프라, 화면 꾸미기
- 스캔 PDF(OCR), HWP 직접 업로드
- 멀티 에이전트 구조 (단일 그래프로 끝낸다)
- 조항 자동 수정안 생성, 법률 자문
- 실제 기업 계약서, SK에코플랜트 내부 자료

## 가정과 검증 방법
| 가정 | 틀리면 생기는 일 | 검증 방법 | 상태 |
|---|---|---|---|
| 검토 담당자가 조항별 대조에 시간을 많이 쓴다 | 문제 자체가 작다 | 건설사·하도급 업체 실무자 인터뷰 2~3명 | ⬜ 미검증 |
| 표준계약서 대비 편차가 "불리한 조항"의 좋은 신호다 | 표준과 다르지만 문제없는 조항이 오탐으로 쏟아진다 | 실제 공개 계약서로 precision 측정 | ⬜ 미검증 |
| 합성 변형(문자열 치환)이 실제 계약서의 불리한 조항을 대표한다 | 합성셋 점수가 실제 성능을 과대평가한다 | 공개 계약서 샘플로 별도 평가 | ⬜ 미검증 (README 한계에 명시) |
| 규칙 판정과 근거 검증이 LLM 단독보다 낫다 | 개선 스토리가 성립하지 않는다 | baseline/v1/v2 비교 | ⬜ API 키 필요 |
