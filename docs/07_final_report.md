## 2. 가장 효과가 컸던 개선: 규칙 레이어

**무엇:** 기한(일수)·비율·배수처럼 숫자로 판정할 수 있는 항목을 LLM 대신 결정적 규칙으로 판정했다. 기준값 14개는 모두 하도급법·표준하도급계약서 원문 인용을 갖고 있고, 인용이 원문에 실제로 있는지 테스트가 확인한다.

**효과 (set-v2, v1 → v2):** Recall 0.92 → 1.00, Precision 0.92 → 1.00. v1 의 누락 2건과 오탐 2건이 모두 사라졌다.

**왜 효과가 있었나:**
- 같은 변형("증액분 지급 기한 15일 → 60일")을 LLM 은 set-v1 계약서 02 에서는 `design_change` 로, set-v2 계약서 02 에서는 `payment_deadline` 으로 분류했다. 조항 내용은 같고 주변 조문 번호만 달랐다. **LLM 분류는 문맥에 따라 흔들리고, 규칙은 같은 입력에 항상 같은 답을 낸다.**
- 규칙 결과를 LLM 프롬프트에 "이미 찾은 것"으로 넘겨서 LLM 이 같은 조항을 다른 카테고리로 중복 보고하지 않게 했다 → 오탐 감소.
- 반대로 **근거 검증 레이어는 효과가 관측되지 않았다**(폐기 0건). 환각을 줄인 건 검증이 아니라, 검색으로 표준 원문을 프롬프트에 넣어준 것(baseline → v1 근거 정확도 0.00 → 1.00)이었다.

## 3. 알려진 한계 3가지

1. **합성 데이터의 한계.** (공정위 실제 문구 5건으로 확인한 결과, 탐지는 유지됐지만 baseline 도 5/5 를 잡아 파이프라인의 우위는 보이지 않았다.) 평가 계약서는 표준계약서에 문자열 치환으로 변형을 넣은 것이라 실제 계약서보다 쉽다(검색 hit@3 1.00). 정답이 24개뿐이라 1건이 4.2%p다. 실제 계약서(문장 재작성, 특약 별지, 표)에서의 성능은 측정하지 않았다.
2. **규칙 레이어는 문형이 표준과 같을 때만 숫자를 읽는다.** 문장을 바꿔 쓰면 규칙은 조용히 빠지고 LLM 판정에 의존한다(오탐은 늘지 않지만 적중이 줄어든다). 지체상금 요율·하자담보 기간 상한은 원문이 없어 규칙에서 제외했다(`TODO(source-needed)`).
3. **정확도의 대가가 크고, 일부 지표는 baseline 이 낫다.** 입력 토큰이 약 5.9배이고, 위험도(high/medium/low) 일치는 baseline 이 가장 높다(0.73 vs v2 0.62). 처리 시간과 USD 비용은 아직 제대로 재지 않았다.

## 4. 자소서용 요약 3줄 (측정된 것만)

1. **문제:** 하도급 계약서 검토를 LLM 에 통째로 맡기면 근거 조항을 특정하지 못하고(근거 정확도 0%), 기억에 의존한 하도급법 인용 21건 중 5건이 원문과 맞지 않는 문제를 확인했습니다.
2. **내가 한 것:** 조항 분할과 BM25 검색으로 표준 원문을 근거로 붙이고, 기한·비율 같은 숫자 항목은 원문 인용이 달린 기준값 14개로 판정하는 규칙 레이어를 둔 LangGraph 파이프라인을 만들어, 3가지 구성을 같은 평가셋에서 비교했습니다. LLM이 적은 조문 번호를 원문과 대조하는 검증기도 만들어 인용 오류를 자동으로 셌습니다.
3. **결과:** 합성 평가셋(정답 24개)에서 Recall 0.92→1.00, Precision 0.81→1.00, 근거 조항 정확도 0%→100%를 달성했고, 그 대가로 입력 토큰이 약 5.9배 늘어나는 트레이드오프를 함께 측정했습니다.

> 쓸 때 주의: "합성 평가셋", "정답 24개"는 빼지 않는다. 면접에서 바로 확인받는 부분이다.

## 5. 면접 예상 질문 5개와 답변 포인트

### Q1. 평가 데이터를 직접 만들었는데, 그 결과를 믿을 수 있나요?
- **인정:** 합성 데이터라 실제보다 쉽고(검색 hit@3 1.00), 정답 24개라 표본이 작다. 그래서 "실제 성능"이 아니라 **같은 조건에서 구성 간 비교**로만 주장한다.
- **신뢰를 높인 장치:** 변형을 결정적 문자열 치환으로 넣어 라벨이 100% 정확하다. 시드 고정으로 바이트 단위까지 재현된다. 평가셋을 숫자에 맞춰 고치지 않는다는 규칙을 지켰다.
- **실제 사례:** 결과를 보다가 생성기 버그(조문 참조 재번호 누락)를 찾았다. 원본(set-v1)은 그대로 두고 버그만 고친 set-v2 를 따로 만들어, 오탐 3건이 데이터 탓이었음을 분리해서 보였다.
- **다음 단계:** 공개된 실제 계약서 샘플과 문장을 다시 쓴 어려운 변형으로 일반화 성능을 잰다.

### Q1-1. 실제 계약서에서도 되나요?
- 실제 계약서는 거의 공개되지 않아서, 공정위 의결서에 인용된 **실제 부당특약 문구 5개**(유강종합건설·지원건설·대방건설)로 시험했다. 채점 기준은 결과를 보기 전에 고정해서 커밋했다.
- 결과: 세 구성 모두 5/5 탐지, 표준 조항 오탐 0. **하지만 baseline 도 5/5 였다.** 노골적인 특약은 LLM 혼자도 잘 잡는다.
- 배운 것: 파이프라인의 가치는 "탐지"보다 **근거의 정확성**과 **미묘한 숫자 변경**(합성셋의 60일→90일 같은)에 있다. 실제 문구에서 검색이 대금 지급 조항을 놓친 약점도 확인했고, 그 개선은 이 5건이 아닌 별도 문구로 검증해야 한다.

### Q2. 환각은 어떻게 막았나요?
- **솔직하게:** LLM 인용이 원문에 실제로 있는지 코드로 검증하는 레이어를 만들었지만, 이번 평가에서는 **버린 건이 0건**이었다. Sonnet 의 인용은 모두 실존했다.
- **실제로 효과가 있었던 것:** 검색으로 표준 원문을 프롬프트에 넣어준 것. 조문 인용 검증기로 세면 baseline 은 인용 오류 40건(하도급법 조문 오류 7건, 없는 "제40조" 포함), v1·v2 는 0건이었다. baseline(원문 없음)은 근거 조항 정확도 0.00, 하도급법 인용 21건 중 5건이 원문과 불일치. 예: "15일 이내 지급"을 제13조 제6항이라 했지만 원문은 제3항이고 제6항은 어음 할인료 조항이다.
- **설계 원칙:** 숫자 기준값은 아예 원문 인용과 함께 파일로 두고 테스트로 존재를 강제했다. "모델이 맞게 기억하길 기대"하지 않고 "원문을 보게" 만들었다.
- **한계:** 인용이 실존하는지만 보고, 그 인용이 지적을 실제로 뒷받침하는지는 검증하지 않는다.

### Q3. 왜 LangGraph 를 썼나요? 일반 함수로도 되지 않나요?
- **인정:** 지금 구조는 직선형이라 함수 연결로도 된다.
- **쓴 이유:** baseline / v1 / v2 를 **같은 그래프 코드에서 경로만 바꿔** 비교했다. 노드별 입출력을 pydantic 으로 고정해서 상태를 추적하기 쉬웠다.
- **LangGraph 를 쓸 이유가 분명해지는 다음 단계:** 근거 검증 실패 시 다른 표준 조항으로 재판정하는 루프, 규칙과 LLM 판정이 충돌할 때 사람 검토로 보내는 조건부 분기.

### Q4. 토큰이 5.9배인데 실무에 쓸 수 있나요?
- **측정 사실:** 계약서당 입력 토큰 43.6k → 257.9k. 조항마다 표준 조항 후보 3개를 함께 넣기 때문이다.
- **줄일 방법:** ① 표준과 글자가 같은 조항은 LLM 호출 생략(단, 합성셋에선 이게 점수를 부풀리므로 실제 데이터로 검증 필요) ② 후보를 3개 → 1개로 ③ 1차 분류는 작은 모델, 의심 조항만 큰 모델 ④ 같은 표준 조항 프롬프트 캐싱.
- **판단 기준:** 검토 담당자가 조항 50개를 직접 대조하는 시간과 비교해야 한다. 그래서 시간·USD 비용 측정이 다음 할 일이다.

### Q5. 혼자 AI 와 개발하면서 가장 크게 배운 점은?
- **실패:** 설계부터 시작하고 준비물(API 키) 확인을 미뤄 MVP 마감을 넘겼다.
- **바꾼 것:** 기획 → 요구사항 → 설계 → **준비물 게이트** → 구현 → 검증 순서를 정형화하고, 요구사항 ID 를 테스트까지 잇는 추적표를 만들었다.
- **AI 협업 방식:** 실제 실행 전에 가짜 키로 드라이런해서 모델 설정 버그(temperature 거부)를 미리 잡았고, AI 가 낸 추정치를 원문 대조로 정정한 경험이 있다. AI 결과도 측정하고 검증해야 한다는 걸 체득했다.
